# 사건 신원 — 주소를 내용에서 떼어낸다 (D1·D2)

> 2026-09-12. Story 계획 A(#103) → 메뉴 → B(#104) → C(#105·#106) 다음 단계.
> **이 문서가 D 단계의 정본이다.**

## 0. 왜 D 인가 — 이름 정리부터

지금 저장소에 "C" 라는 글자가 **두 가지 뜻으로** 살아 있다.

| 출처 | C 의 뜻 | 상태 |
|---|---|---|
| Story 계획 (2026-09-06) | `A 원장 → 메뉴 → B 변화이력 → C 재현율` | **C 완료** (#105, 자격 0.331→0.375, 목표 0.35 통과) |
| Story 장기기억 메모 (2026-09-12) | `C1 Evidence Recall … C9 Follow` | 착수 전 |

같은 글자가 다른 것을 가리키면 반드시 사고가 난다. **기존 계획을 이어 D/E/F 로 가고,
메모의 C1~C9 는 그 안에 흡수한다.** 메모의 C2(Event 안정성)+C3a(판정 영속화)가 이
문서의 D 다.

## 1. 진단 — 세 번 고쳐 잡았다

### 틀린 진단 ① "장기 기억이 없다"

메모는 5년 기억을 새로 짓자고 한다. 그런데 라이브(`20260912T113019Z`, 525건)를 보면
**수명이 두 개**고 긴 쪽은 이미 있다.

```
회차 수명 (briefing_count · first_seen..last_seen)
  1회차 421/525 (80.2%) · 중앙값 0일 · >21일 16건 · 최대 46일

근거 수명 (related_articles 의 article_date 범위)
  n=273 · 중앙값 11일 · >7일 159건 · >21일 55건 · 최대 48일
  그중 briefing_count==1 인 것이 16건 ← 48일치를 모아 놓고 '단발'로 센다
```

#105 가 만든 것이 아래쪽이다. **21일을 넘는 사건 묶음이 이미 55건 있다.** 없는 것은
장기 기억이 아니라 그 묶음을 부를 **이름**이다.

### 틀린 진단 ② "지문이 판정한다"

메모 7절은 `same_event`/`same_story` 지문 규칙 분리를 제안한다. 라이브 매칭 경로:

```
llm_approved 815 (44.2%) · tags 593 · title_tags 178 · embedding 124
title 123 · manual 4 · legacy 2 · story_id 1 · story_fingerprint 2 (0.1%)
```

지문은 1,842건 중 **2건**이다. 회색지대를 LLM 이 흡수했다(`issue_llm_reviews.json`
15,134건 캐시 · `same_event=True` 3,209건 · 각각 한국어 이유 한 줄). 즉 메모가
C4~C6 에서 만들자던 "후보를 다시 판단하는 판정기"와 "왜 연결됐는지"(#20)의 재료가
**이미 있다.** 없는 것은 그 판정이 기사 해시 쌍 위에 놓여 있다는 점이다 — 기사가
창 밖으로 나가면 판정도 사라진다.

### 진짜 진단 — 신원이 내용에 딸려 있다

`cluster_selected_articles` 는 매 빌드 카탈로그를 처음부터 재조립하고, id 는 그때
첫 멤버의 해시로 만든다(`issue-{hash}`, 실측 516/525 가 멤버 해시 파생). 그래서
묶음이 한 칸만 달라지면 주소가 바뀐다.

```
9/1 빌드 447건 ↔ 9/12 라이브 525건
   사라진 id 75건 (16.8%) · 표본 5건 전부 HTTP 404
   사라진 것의 first_seen 은 창 한복판(08-26~08-31) → 노화가 아니다
   발행된 rss.xml 의 고유 이슈 링크 185건 중 33건(17.8%)이 이미 깨져 있었다
```

그런데 같은 대조에서 **75건 전부** 제 근거 기사를 지금 어느 이슈가 들고 있는지
말할 수 있었다(소유자 1개 59건 · 2개 이상 16건 · 못 찾음 **0건**).

> **id 가 죽은 것이 아니라, 살아 있는 증거를 아무도 묻지 않았다.**

`issue_ledger` 는 그 이동을 이미 기록하지만 **사후**에 리다이렉트를 만든다.
D 는 같은 증거를 **id 를 정하기 전에** 물어 이동 자체를 없앤다.

## 2. 무엇을 만들었나

### `event_identity.py` — 신원 authority

증거는 **기사 해시뿐이다**(제목 유사도 금지 — 오병합을 주소 체계에 들인다).
해시가 배타적이어야 성립하므로 확인했다:

```
related_articles 의 해시  →  두 이슈가 함께 가진 것   0건  (배타적 ✔)
story_members 의 해시     →  두 이슈가 함께 가진 것 120건  (공유됨 ✘ — 쓰지 않는다)
```

규칙 다섯:

1. 소유자 없음 → **발급** (지금 동작 그대로)
2. 소유자 하나 → **상속**
3. 소유자 둘 이상(병합) → **`first_seen` 이 가장 이른 쪽**. 큰 쪽이 아닌 이유:
   묶음 크기는 늘고 줄어 id 가 왕복하지만 최초 관측일은 단조롭다. 그리고 오래된
   주소일수록 밖에 나가 있다(RSS·인용). 진 id 는 `identity_merged_from` 에 남고
   원장이 리다이렉트를 세운다.
4. 한 옛 id 를 두 묶음이 주장(분열) → 공유 해시가 많은 쪽. 동수면 가장 이른 기사를
   가진 쪽. 진 쪽은 발급 + `identity_split_from`.
5. **발급도 충돌한다.** 재생 중 실제로 났다 — 발급 묶음의 임시 id 가 다른 묶음이
   물려받은 옛 id 와 같을 수 있다. 상속이 우선권을 갖고 발급이 대표 해시로 비켜선다.

### `issue_ledger.py` — 두 군데

* **해시를 덮지 않고 쌓는다.** 부착은 빌드마다 흔들리므로(#105 실측: 같은 id 로
  살아남은 372건 중 56건이 근거 215건을 잃었다) 덮으면 다음 빌드가 같은 사건을
  못 알아본다. 이른 것이 앞에 남는다 — 최초 기사가 신원 앵커다.
* **`last_written` 을 남긴다.** 소유권 판정 기준이 `last_seen` 이면 안 된다 —
  그건 카탈로그가 말한 이슈의 활동일이라 여러 이슈가 같은 값을 갖고, 동값 비교가
  제비뽑기가 된다.

  ```
  last_seen    기준: 버린 해시 378/2733 (13.8%) · 3회차 id 유지 524/525
  last_written 기준: 버린 해시 471/2733 (17.2%) · 3회차 id 유지 525/525
  ```

  **더 많이 버리고 더 정확하다.** 동값을 억지로 가르면 일부가 틀리고, 틀린 소유권
  하나가 다음 빌드에서 주소를 옮긴다. 버린 해시는 그 묶음의 다른 해시가 말해 준다.

### `web/build_data.py` — 한 자리

2차 묶음과 근거 부착이 끝난 뒤, `resolve_local_issue_id_conflicts` **앞**에 선다.
그 자리여야 묶음의 해시 집합이 확정돼 있고 중복 id 검사가 상속 결과까지 본다.
묶음 모양은 건드리지 않으므로 p1 서명(대표 해시·대표 제목·카드 해시)과 무관하다.

판정 근거를 카탈로그 행에 싣는다 — `identity_origin` · `identity_evidence` ·
`identity_merged_from` · `identity_split_from`. 되돌리려면 무엇을 되돌리는지
읽을 수 있어야 한다(메모 #14).

### `story_fingerprint.reported_event_date()` — 함정 막기

`story_fingerprint.event_date` 는 `AXES` 에 없어 **읽는 코드가 하나도 없다.** 그래서
무결성 게이트도 지나지 않는다. delivery_log 801건 실측:

```
지문에 채워진 것 124건 · 발송연도−사건연도=0 이 70건 · **=2 가 33건(26.6%)**
   2026-08-16 발송  event_date=2024-08-14  테라파워-한국 기업 SMR 협력
   2026-08-21 발송  event_date=2024-08-20  국회, 전력망 특별법 등 70건 처리
```

지금은 안 읽어서 무해하고, 타임라인을 이 칸에 세우는 순간 해롭다(메모 #11). 원시
칸을 직접 읽지 말고 접근자를 쓴다 — 연도가 기사일과 두 해 이상 어긋나면 빈 값이다.

실제 delivery_log 에 돌린 결과: 124건 → 통과 83(연도차 −1/0/+1) · 차단 41
(연도차 −4·−3·−2·+2, **2년 오기 33건 전부 포함**).

> 최상위 `event_date` 는 이미 강한 게이트가 있다(선언 출처 + 원문 날짜 표기 대조;
> 실측 427건 중 361건을 비운다). 고칠 곳은 그쪽이 아니었다.

## 4. 하지 않은 것과 그 이유

### git 저장 — 진단이 틀렸고, 이번에 건드리지 않는다

"봇 커밋이 `curated.json` 169,205줄을 재작성한다"고 봤는데 **틀렸다.** 그 커밋의
의미상 변화는 항목 24건 추가 / 24건 삭제, 공통 항목 내용 변화 0, 키 순서 유지였다.
그리고 `git repack --depth=250 --window=250` 은 193MB → 181MB (6%) 뿐이었다 —
델타 설정 문제가 아니다.

실제 비용(최근 7일에 새로 생긴 blob 의 pack 비용):

```
합계 29.8 MiB → 일 4.26 MiB
  curated.json          10.63 MiB  ← 14일 만료 롤링 캐시
  digest_queue.json      5.18 MiB  ← 큐
  archive/2026-09.jsonl  5.05 MiB  ← 진짜 새 자료 (불가피)
  fonts                  2.66 MiB  ← 일회성
  issue_llm_reviews.json 1.48 MiB
```

누적 179.7 MiB 중 112.9 MiB(63%)가 `archive/2026-08.jsonl` 인데 그건 **이미 닫힌
달**이라 더 자라지 않는다.

정리하면: 상위 두 개가 **만료되는 캐시와 큐**이고 그 git 이력은 가치가 없다.
그런데 git 은 Actions 런 사이의 **유일한 DB** 다(`admin_overrides` 머리말:
"KV 가 버퍼, git 이 여전히 DB"). 17MB 롤링 캐시를 꺼내는 것은 캐시 미스 때 14일치
큐레이션을 잃는 별도 PR 이다. **신원 변경과 묶지 않는다.**

### 애널리틱스 — 켜지 않는다

`story-menu-launch` 의 미결 결정 그대로다(애널리틱스 0건 · 사이트 전체
`noindex,nofollow`). 비콘을 켜는 것은 방문자 데이터를 제3자에 보내는 일이라
사람이 결정할 사안이고, 토큰도 사람 손에 있다.

### 화면 — 아직 아무것도 안 보여준다

`identity_origin` 등은 감사·진단용으로만 실린다. 메모 #20("왜 이 Story 에
포함됐나")을 화면에 세우는 것은 E 단계다 — 재료(LLM 이유 3,209건)는 이미 있다.

## 5. 다음 — E 단계

D 가 못을 박았으니 E 는 **창이 진짜 벽인지 먼저 재는 것**이다. 장기 인덱스를
짓기 전에.

1. **E1 창 확장 재측정.** 근거 span 이 21/42/48일에서 끊기는 모양을 확인하고

   **이 숫자가 F(장기 Story)를 열지 말지 정한다.**
2. **E2 정답지의 집.** 지금 못 재는 것이 셋 — 수집 재현율(정답지 `2026-08-06`
   하루뿐), Event precision/recall, Story recall. `.eval/` 은 `.gitignore` 라
   사람 판정이 컴퓨터를 옮기면 날아간다(이미 37건 대기). 씨앗은 LLM 판정 캐시

3. **E3 임베딩 보존.** `EMBEDDING_RETENTION_DAYS = 35` 라 벡터가 35일에 지워진다.
   그리고 로컬 벡터는 IDF 를 그 빌드 코퍼스로 계산하므로 **빌드 간 같은 공간이

### D4 — 저장한 이슈의 옛 주소 복구 (완료)

**범위를 먼저 정정했다.** `nuclens-follows`·`nuclens-follow-seen` 은 `issue_id` 가
아니라 **`entity_id`** 키다(`toggleFollow(entityId)` · "이번 범위의 팔로우는 엔티티
한정이다"). 엔티티 id 는 이 이동과 무관하므로 팔로우는 깨지지 않았다.

`issue_id` 를 키로 쓰는 것은 둘이다.

| localStorage | 성격 | 처리 |
|---|---|---|
| `nuclens-saved-issues` + `-meta` | 사용자가 **의도적으로** 저장 | **복구한다** |
| `nuclens-recent-issues` | 발자취(MRU 8) | 그대로 둔다 — "발자취는 복구 대상이 아니다"(기존 결정) |

저장 쪽은 이미 비파괴 처리가 있었다 — 살아 있는 목록에 없으면 스냅샷 묘비를 세워
제목으로 다시 찾게 한다(`savedTombstone`). 그 자리에 **자동 복구**를 넣는다.

**리다이렉트로는 안 고쳐진다.** 그건 주소를 직접 열 때만 작동하고 localStorage 에
키로 박힌 값은 구해 주지 못한다. 그래서 원장의 별칭표를 앱이 읽는다.

* 빌드: `build_issue_pages` 가 이미 계산하는 `issue_ledger.redirects` 를
  `data/issue_aliases.json` 으로 낸다. **대상이 살아 있는 이슈인 것만** 싣는다 —
  보관 페이지로 가는 별칭은 앱이 `issues.json` 에서 못 찾으므로 옮겨 줘도 그릴
  것이 없다(실측: redirects 89건 중 live 대상 72건, 3.6 KB).
* **`meta.json` 에 넣지 않는다.** 원장은 계속 자라므로 첫 화면에서 통째로 받는
  파일에 넣으면 상한이 사라진다 — 보관 스냅샷과 같은 판단이다. 앱은 **묘비가
  생길 때만** 이 파일을 받고, 한 번 받으면 세션 동안 다시 받지 않는다.
* 앱: `resolveAlias` 가 사슬을 따라가고(A→B→C, 고리를 만나면 멈춘다),
  `migrateSavedIds` 가 옮겨 적는다. 살아 있는 id 는 별칭표에 옛 항목이 남아
  있어도 건드리지 않는다 — 현재 카탈로그가 이긴다.

스냅샷 병합에서 버그가 하나 나왔고 검사가 잡았다: 옛 id 와 새 id 를 **둘 다**
저장해 둔 사람에게 옮겨 온 옛 스냅샷이 직접 저장한 값을 덮어 제목·날짜가 과거로
되돌아갔다. **그 id 로 직접 저장한 것이 먼저다**로 고쳤다.

실제 별칭표(72건)로 끝까지 확인: 옛 id 10건을 저장해 둔 사용자의 **묘비 10건 → 0건**
(10건이 9개 현재 이슈로 접힌다 — 둘이 같은 이슈로 합쳐졌다). 스냅샷 9건 보존.

검사 16건(`web/tests/saved_alias_migration.mjs`)을 `python-tests.yml` 과
`deploy-web.yml` 양쪽에 걸었다. 후자는 빌드 뒤라 산출된 별칭표의 모양까지 본다.
