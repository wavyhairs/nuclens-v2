# 화면 v3 — 1차 이후로 미룬 것

작성: 2026-09-15 · 대상 PR: 「Nuclens UI V3 — 1차 개편」

1차에서 **일부러 손대지 않은** 두 가지다. 둘 다 고쳐야 하지만, 지금 v3 작업과 섞으면
작은 UI 개편이 번들러·데이터 파이프라인 개편으로 커진다. 근거를 여기 남겨 다음 사람이
처음부터 다시 재지 않게 한다.

---

## 1. 첫 화면 번들 — JS/CSS code splitting 검토

**상태**: 미착수 · 우선순위 보통

A6 에서 첫 렌더 차단 바이트를 gzip 4.90 MB → 209 KB 로 줄였다. 목표는 200 KB 였고
**9 KB 를 넘겼다.** 남은 209 KB 의 구성:

| 파일 | gzip | 비고 |
|---|---:|---|
| `app.js` | 101 KB | 5,700줄 단일 파일. 다섯 화면과 차트·달력·워드클라우드가 한 벌 |
| `style.css` | 53 KB | 3,900줄. v3 블록은 그중 240줄 |
| `today.json` | 42 KB | A6 산출물. **데이터 쪽은 여기서 끝났다**(원래 37 MB) |
| `ui-v3.js` | 13 KB | |

즉 이제 첫 화면을 붙잡는 것은 **데이터가 아니라 코드**다. 9 KB 를 억지로 깎는 것은
의미가 없고, 제대로 하려면 둘 중 하나다.

- `app.js` 를 화면 단위로 쪼개고 비활성 탭을 지연 로드
- v3 전용 진입점을 따로 만들어 구 화면 코드를 v3 경로에서 빼기

둘 다 지금은 빌드 도구가 없는 이 저장소에 번들러를 들이거나(`web/public/*` 는 지금
소스가 곧 배포본이다) 수동 분할 규약을 새로 세우는 일이다. **v3 가 기본 화면이 된
뒤에** 하는 것이 맞다 — 그때는 구 화면 코드를 지울 수 있어서 쪼개지 않고도 많이 준다.

착수 전 다시 잴 것: `node web/tools/measure_ui.mjs "?ui=v3"` 의 `blockingBytes`.

## 2. 장기 스토리 사건 원장 일원화 및 ghost ID 정리

**상태**: 미착수 · 우선순위 높음 (데이터 정합성)

`threads.json`(장기 스토리)과 `issues.json`(이슈 원장)이 같은 사건을 다르게 말한다.
A4 에서 **고치지 않고 기록만 했다** — 화면 작업과 섞으면 판정 엔진 수정이 된다.

### 실측 (로컬 스냅샷 2026-09-13)

| 항목 | 값 |
|---|---|
| 스토리 수 | 101건 |
| 이슈 원장과 시작일 또는 건수가 **다른** 스토리 | **97건 (96%)** |
| 이슈 원장에 없는 `event_id` 를 가리키는 스토리 | 다수 (아래 사례) |

사례 — 「미국 원자력 기업 웨스팅하우스, 기업공개(IPO) 신청」 (사건 7건):

| 날짜 | 사건 제목 | 이슈 원장 |
|---|---|---|
| 08-02 | 웨스팅하우스, 기업공개(IPO) 신청 | 있음 |
| 08-28 | 정부, 대미 투자 1호 사업 22억 달러 … 지분 인수 | 있음 |
| 08-30 | 대미 투자 협상 난항 … | 있음 |
| 09-04 | 웨스팅하우스, IPO 신청 및 신규 원전 사업 구조 개편 | 있음 |
| 09-08 | 한수원-웨스팅하우스, 미국 내 원전 8기 건설 협력 잠정 합의 | 있음 |
| 09-09 | 정부, 대미 투자 1호 사업 22억 달러 … 지분 인수 | **없음** |
| 09-10 | 한수원-웨스팅하우스, 미국 내 원전 8기 건설 협력 잠정 합의 | **없음** |

마지막 두 건은 앞선 사건과 **제목이 같다**(08-28↔09-09, 09-08↔09-10). 새 사건이
아니라 원장에서 옮겨 간 id 의 유령이고, 스토리는 그 옛 주소를 계속 들고 있다.
결과적으로 스토리의 사건 수가 실제보다 부풀고, 그 링크는 죽는다.

### 방향 (결정됨)

`threads.json` 이 사건을 **독립적으로 보관하는** 지금 구조 대신, `issues.json` 의
사건 ID 를 **정본으로 참조**하도록 간다. 스토리는 사건을 소유하지 않고 묶기만 한다.

그러면 원장이 id 를 옮길 때(`moved_to`) 스토리가 자동으로 따라가고, 유령이 생길 자리가
없어진다. 지금은 두 곳이 각자 사건 목록을 들고 있어서 반드시 갈라진다.

### 작업 범위 (예상)

- `thread_ledger.py` · `thread_judge.py` — 사건 목록을 id 참조로 바꾼다
- `threads.json` 스키마 — `events[].event_id` 를 원장 조회 키로만 쓰고 제목·날짜는 싣지 않는다
- 원장의 `moved_to` 가 사건 계층으로 새지 않게 하는 게이트(관련: 장기 스토리 β 화면에서
  링크 46% 가 죽었던 원인)
- 마이그레이션 — 기존 스토리의 유령 id 를 원장의 현재 주소로 옮기거나 떨군다

### 이번 작업과의 관계

v3 는 이 문제를 **피해 갔다**. 3단 시트의 타임라인은 `issues.json` 하나만 읽고
(`?view=longterm&th=` 딥링크로 들어올 때만 기존 장기 스토리 화면이 선다), 탐색의
'오래 이어진 이슈' 정렬도 원장의 `first_seen`~`last_seen` 만 쓴다. 그래서 이 정리를
먼저 하지 않아도 v3 가 틀린 말을 하지는 않는다 — 다만 장기 스토리 화면은 여전히 틀린다.
